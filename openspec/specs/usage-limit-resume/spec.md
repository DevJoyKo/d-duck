# usage-limit-resume Specification

## Purpose
Claude 사용량 한도에 걸려 멈춘 작업을 사용자에게 알린다. 한도가 리셋되면 D.Duck이 시작한 백그라운드 작업을 안전 조건 안에서 자동으로 이어서 실행한다.

## Requirements

### Requirement: 한도 감지
- 수집기는 다음 조건을 모두 만족하는 transcript 레코드를 한도 도달로 판정해야 한다(SHALL): `type`이 assistant, `isApiErrorMessage`가 true, `error`가 `rate_limit`, `quotaLimits.status`가 `rejected`.
- 리셋 시각은 `quotaLimits.resetsAt`(UTC 초)에서 읽는다. 없을 때만 `apiErrorParams.rate_limit_info.resetsAt`에서 읽어야 한다(SHALL).
- 저장하는 값은 다음뿐이어야 한다(SHALL): 레코드 uuid, 세션 id, 서브에이전트 여부, 시각, 리셋 시각, 한도 종류. 한도 종류는 허용 목록 값이고, 그 밖은 `other`로 저장한다.
- 메시지 본문, `upgradePaths`, overage 필드, cwd, 브랜치는 읽거나 저장하지 않아야 한다(MUST NOT).
- 같은 (세션, 리셋 시각)의 기록은 하나의 한도 사건으로 묶어야 한다(SHALL). 메인 세션 기록과 서브에이전트 기록도 여기에 포함된다.
- 리셋 시각이 다음 중 하나면 "리셋 시각 모름"으로 기록해야 한다(SHALL): 없음, 레코드 시각보다 앞섬, 레코드 시각보다 8일 넘게 뒤.

#### Scenario: 5시간 한도
- **WHEN** 세션 transcript에 assistant 레코드가 추가된다: `error: "rate_limit"`, `quotaLimits: {status: "rejected", resetsAt: 1794113400, rateLimitType: "five_hour"}`
- **THEN** 그 세션에 한도 사건이 하나 생긴다(리셋 시각 1794113400초, 종류 five_hour)
- **AND** DB·WAL·로그에 메시지 본문 카나리 문자열이 없다

#### Scenario: 메인과 서브에이전트 기록
- **WHEN** 같은 세션의 메인 파일과 서브에이전트 파일에 같은 리셋 시각의 한도 레코드가 하나씩 생긴다
- **THEN** 한도 사건은 하나다

#### Scenario: 같은 레코드 다시 읽기
- **WHEN** 같은 파일을 처음부터 다시 수집한다
- **THEN** 레코드 uuid가 같아 기록이 늘지 않는다

#### Scenario: 리셋 시각 없음
- **WHEN** 한도 레코드에 `quotaLimits`와 `apiErrorParams`가 모두 없다
- **THEN** "리셋 시각 모름" 사건이 생긴다
- **AND** 자동 재개 예약은 만들지 않는다

### Requirement: 한도 알림
- 설정 "사용량 한도 알림"이 켜져 있으면(기본 켬), 리셋 시각이 미래이고 아직 알리지 않은 (세션, 리셋 시각)에 대해 OS 알림을 보내야 한다(SHALL).
- 한 수집 주기에 같은 리셋 시각의 사건이 여러 개 생기면 알림 하나로 묶어야 한다(SHALL).
- 앱이 처음으로 전체 수집(백필)을 할 때는 알림을 보내지 않아야 한다(MUST NOT). 그때 본 사건은 이미 알린 것으로 표시해야 한다(SHALL).
- 알림 본문에는 다음만 담아야 한다(SHALL): 고정 문구, 리셋 시각(로컬), 이어서 할 작업 수, 직접 이어야 하는 작업 수. 리셋이 24시간보다 멀면 리셋 시각에 날짜·요일을 넣어야 한다(SHALL).
- 자동으로 이을 작업이 있으면 "Mac이 깨어 있어야 이어요"를 넣어야 한다(SHALL).
- 세션 제목, 경로, 모델이 쓴 글은 담지 않아야 한다(MUST NOT).

#### Scenario: 작업 3개가 동시에 한도
- **WHEN** 같은 리셋 시각으로 세 세션이 한도에 닿는다
- **AND** 그중 두 개는 자동 재개 대상이고 하나는 대상이 아니다
- **THEN** OS 알림 하나만 뜬다: "사용량 한도에 닿았어요 · 오후 1:50 리셋 · 2개는 이어서 할게요 · 1개는 직접 이어야 해요 · Mac이 깨어 있어야 이어요"

#### Scenario: 자동 재개를 꺼 둠
- **WHEN** 자동 재개 설정이 꺼진 상태에서 두 세션이 한도에 닿는다
- **THEN** 알림은 "사용량 한도에 닿았어요 · 오후 1:50 리셋 · 2개는 직접 이어야 해요"이다
- **AND** "Mac이 깨어 있어야 이어요"는 없다

#### Scenario: 주간 한도
- **WHEN** 리셋 시각이 사흘 뒤다
- **THEN** 알림의 리셋 시각이 "11월 12일(목) 오전 9:00" 꼴이다

#### Scenario: 처음 켤 때
- **WHEN** 리셋 시각이 아직 미래인 한도 기록이 있는 transcript를 처음 수집한다
- **THEN** 알림이 뜨지 않는다
- **AND** 배너에는 보인다

#### Scenario: 같은 사건 다시 보기
- **WHEN** 이미 알린 (세션, 리셋 시각)의 레코드가 또 수집된다
- **THEN** 알림이 다시 뜨지 않는다

### Requirement: 한도 배너와 카드 표시
- 리셋 시각이 미래인 한도 사건이 있으면, 작업 화면은 위쪽 배너에 한 줄로 보여 줘야 한다(SHALL): 리셋 시각(로컬, 24시간 넘게 남으면 날짜·요일), "N개는 이어서 할게요", "M개는 직접 이어야 해요". 0개인 쪽은 빼야 한다(SHALL).
- 자동으로 이을 작업이 있으면 배너에 "Mac이 깨어 있어야 이어요"를 넣어야 한다(SHALL).
- 자동 재개 예약이 있는 작업 카드는 "한도 대기 · <시각>에 이어서" 칩과 "이번엔 안 이어요" 동작을 보여 줘야 한다(SHALL).
- 직접 이어야 하는 작업 카드는 "지금 이어서" 버튼과 이유 한 줄을 보여 줘야 한다(SHALL).
- 리셋 시각을 모르면 "리셋 시각을 몰라요"와 직접 잇기 버튼을 보여 줘야 한다(SHALL).

#### Scenario: 섞인 배너
- **WHEN** 자동 재개 대상 2개와 위험 권한 작업 1개가 한도로 멈췄다
- **THEN** 배너에 "사용량 한도 · 오후 1:50 리셋 · 2개는 이어서 할게요 · 1개는 직접 이어야 해요 · Mac이 깨어 있어야 이어요"가 보인다

#### Scenario: 자동 재개 꺼짐 배너
- **WHEN** 자동 재개 설정이 꺼진 상태에서 작업 2개가 한도로 멈췄다
- **THEN** 배너에 "사용량 한도 · 오후 1:50 리셋 · 2개는 직접 이어야 해요"가 보인다
- **AND** 두 카드에 직접 잇기 버튼이 있다

### Requirement: 자동 재개 대상
자동 재개는 설정 "리셋되면 자동으로 이어서 하기"(기본 켬)가 켜져 있을 때만 해야 한다(SHALL). 대상은 다음을 모두 만족하는 작업뿐이어야 한다(SHALL):
- D.Duck이 시작한 백그라운드 작업이다.
- 한도 사건이 그 세션의 마지막 정상 응답 이후에 있다.
- 작업별 끄기가 없다.
- 처음 작업 기준 누적 자동 재개가 3번 미만이다.
- 사용자가 D.Duck에서 멈추지 않았다.
- 작업 유형이 배포가 아니다.
- 원격 조작 작업이 아니다.
- 권한 모드가 auto·bypassPermissions라면, 시작 확인 창에서 "리셋 후 자동으로 이어서 하기"를 체크한 작업이다.

추가 규칙:
- 재개 직전에 시작 때와 같은 검사를 다시 해야 한다(SHALL): 꺼 둔 에이전트, 페르소나 위험, 엄격 유형 제한, 원격 조작. 하나라도 걸리면 자동으로 잇지 않고 직접 잇기로 돌려야 한다(SHALL).
- 직접 잇기는 버튼과 네이티브 확인 창을 거쳐야 한다(SHALL).
- 대화형 세션과 D.Duck 밖에서 시작한 세션은 알림·배너만 하고 자동으로 잇지 않아야 한다(MUST NOT).

#### Scenario: 사용자가 멈춘 작업
- **WHEN** 한도 대기 중인 작업을 사용자가 D.Duck에서 멈춘다
- **THEN** 그 작업의 예약이 취소되고 리셋 후에도 이어지지 않는다

#### Scenario: 이미 직접 이어서 함
- **WHEN** 리셋 전에 그 세션에서 한도 시각 뒤의 정상 응답이 수집된다
- **THEN** 예약이 "이미 이어서 했어요"로 닫히고 재개하지 않는다

#### Scenario: 체크 없이 시작한 위험 권한 작업
- **WHEN** bypassPermissions로 시작하면서 확인 창의 "리셋 후 자동으로 이어서 하기"를 체크하지 않은 작업이 한도에 닿는다
- **THEN** 자동 재개 예약이 없다
- **AND** 카드에 "지금 이어서" 버튼이 있고, 누르면 네이티브 확인 창을 거친 뒤에만 이어진다

#### Scenario: 체크하고 시작한 auto 작업
- **WHEN** auto 모드 확인 창에서 체크하고 시작한 작업이 한도에 닿는다
- **THEN** 다른 조건을 만족하면 자동 재개 예약이 생긴다

#### Scenario: 시작 뒤 페르소나 위험이 생김
- **WHEN** 대기 중에 그 작업 페르소나의 정의에 `permissionMode: bypassPermissions`가 추가된다
- **THEN** 리셋 후 자동으로 잇지 않는다
- **AND** 카드가 직접 잇기로 바뀐다

#### Scenario: 배포 작업
- **WHEN** 배포 유형 작업이 한도에 닿는다
- **THEN** 확인 창 체크와 관계없이 자동 재개 예약이 없다

#### Scenario: 터미널 세션
- **WHEN** VS Code나 터미널의 대화형 세션이 한도에 닿는다
- **THEN** 알림과 배너만 보이고 D.Duck은 그 세션을 실행하지 않는다

#### Scenario: 횟수 상한
- **WHEN** 같은 작업이 자동 재개 뒤 세 번째로 다시 한도에 닿는다. 재개로 bg id가 바뀌었어도 마찬가지다.
- **THEN** 더는 예약하지 않는다
- **AND** "자동으로 3번 이어서 멈췄어요" 알림과 카드 표시가 남는다

### Requirement: 재개 실행
재개 시점:
- 리셋 시각 뒤 60~180초 사이 무작위 지연 후 시작해야 한다(SHALL).
- 작업 사이에 20초 이상 간격을 두고, 동시에 3개까지만 시작해야 한다(SHALL).

인자:
- 실행 폴더는 세션의 실제 cwd여야 한다(SHALL).
- 원래 권한 모드를 명시해야 한다(SHALL).
- 세션 지정은 `--resume=<세션 id>`다. 세션 id는 소문자 UUID 형식이고 그 세션 transcript 파일 이름과 같아야 한다(SHALL).
- 시작 때의 팀 규칙, 보고서 지시, 자동 허용 도구를 다시 붙여야 한다(SHALL).
- worktree 생성과 원격 조작 옵션은 다시 붙이지 않아야 한다(MUST NOT).
- 프롬프트는 고정 문구 "사용량이 리셋되어 이어서 진행해요. 멈춘 지점부터 계속해 주세요"여야 한다(SHALL).

자격증명:
- 앱은 Claude 자격증명을 읽거나 넘기지 않아야 한다(MUST NOT). 인증은 CLI가 한다.

중복 방지:
- CLI를 부르기 전에 예약을 "시작 중"으로 점유해, 같은 예약이 두 번 실행되지 않게 해야 한다(SHALL).
- 출력이 사본 세션 시작이면 그 사본을 바로 멈추고 실패로 기록해야 한다(SHALL).
- 재개로 bg id가 바뀌면 새 id를 같은 작업의 별칭으로 기록해야 한다(SHALL). 카드, 보고서, 누적 횟수가 이어져야 한다.

알림·저장:
- 재개를 시작하면 OS 알림 "작업 N개를 이어서 시작했어요"를 한 번 보내야 한다(SHALL).
- 예약 상태 사유에는 고정 코드만 저장해야 하며(SHALL), CLI 출력이나 오류 원문은 저장하지 않아야 한다(MUST NOT).

#### Scenario: 리셋 후 재개
- **WHEN** 리셋 시각에서 2분이 지났고, 대상 작업이 멈춰 있다
- **THEN** CLI가 한 번 실행된다. 인자는 `--bg`, `--resume=<세션 uuid>`, `--permission-mode=<원래 모드>`, 원래 팀 규칙·보고서 지시·`--allowedTools`, 고정 문구다. `--worktree=`와 `--remote-control=`은 없다.
- **AND** 작업 카드가 같은 세션으로 다시 진행 중이 된다

#### Scenario: bg id가 바뀜
- **WHEN** 재개 출력의 bg id가 원래 id와 다르다
- **THEN** 새 id가 같은 작업의 별칭으로 기록된다
- **AND** 카드의 유형·보고서·누적 횟수가 그대로 보인다

#### Scenario: 사본이 시작됨
- **WHEN** 재개 출력이 사본 세션 시작을 알린다
- **THEN** 그 사본이 바로 멈춰진다
- **AND** 예약은 "못 이었어요"로 닫힌다

#### Scenario: 재개 실패
- **WHEN** 재개 실행이 실패하거나 신뢰되지 않은 폴더 오류가 난다
- **THEN** 예약은 "못 이었어요"(고정 코드)로 닫힌다
- **AND** 신뢰 확인 창을 띄우거나 다시 시도하지 않는다
- **AND** 카드에 직접 잇기 버튼이 보인다

### Requirement: 재개 폴더 검증
재개 직전 실행 폴더는 다음 규칙을 따라야 한다(SHALL):
- 세션의 실제 cwd(`agents --json` 또는 transcript의 cwd)를 정규화해 시작 때 기록한 값과 비교한다.
- 작업이 worktree로 시작되었다면 cwd가 `<저장소>/.claude/worktrees/` 아래여야 한다.
- 폴더가 링크면 실패한다.
- Claude 신뢰 여부가 "신뢰됨"으로 확인되지 않으면 실패한다.

하나라도 어긋나면 재개는 실패해야 한다(SHALL). 신뢰 확인 창이나 신뢰 후 재시도로 넘어가지 않아야 한다(MUST NOT).

#### Scenario: worktree가 아닌 곳
- **WHEN** worktree로 시작한 작업의 현재 cwd가 `.claude/worktrees/` 밖이다
- **THEN** 재개하지 않는다
- **AND** 예약은 고정 코드 `cwd_mismatch`로 닫힌다

#### Scenario: 신뢰 미확인
- **WHEN** 폴더의 신뢰 여부를 알 수 없다
- **THEN** 재개하지 않는다
- **AND** 고정 코드 `untrusted`로 닫힌다

### Requirement: 세션 멈추기 조건
- 재개 전에 살아 있는 세션을 멈출 수 있는 경우는 다음을 모두 만족할 때뿐이어야 한다(SHALL):
  - `agents` 목록의 그 행이 백그라운드 종류다.
  - id가 작업의 bg id(또는 별칭)와 같다.
  - 세션 id가 예약의 세션 id와 같다.
- 멈추기 전에 그 transcript를 바로 다시 수집해야 한다(SHALL). 한도 뒤 레코드가 있으면 멈추지 않고 "이미 이어서 함"으로 닫아야 한다(SHALL).
- 누군가 attach해 있는 Idle·WaitingInput 세션은 멈추지 않아야 한다(MUST NOT).

#### Scenario: 사용자가 보고 있는 세션
- **WHEN** 한도로 멈춘 bg 세션에 사용자가 터미널로 attach해 있다
- **THEN** D.Duck은 그 세션을 멈추지도 재개하지도 않는다
- **AND** 예약은 "확인 필요"가 된다

### Requirement: 재시작·늦은 재개
- 예약은 DB에 저장되어 앱을 다시 켜도 유지되어야 한다(SHALL).
- 앱이 꺼져 있거나 Mac이 잠자기였다가 리셋 시각 뒤 2시간 안에 확인하면, 지연 규칙대로 이어야 한다(SHALL).
- 2시간이 넘었으면 자동으로 잇지 않아야 한다. 대신 배너에서 "지금 이어서"·"이번엔 안 이어요"를 고르게 해야 한다(SHALL).
- 고르지 않은 예약은 리셋 뒤 3일이 지나면 만료되어야 한다(SHALL).
- 실행 도중 앱이 꺼져 "시작 중"으로 남은 예약은 다시 실행하지 않아야 한다. "확인 필요"로 바꿔야 한다(SHALL).

#### Scenario: 밤새 꺼져 있던 앱
- **WHEN** 오전 1시 리셋 예약이 있고 앱을 오전 9시에 켠다
- **THEN** 자동으로 잇지 않는다
- **AND** "앱이 꺼져 있어 리셋 때 못 이었어요" 배너에 두 버튼이 보인다

#### Scenario: 잠깐 꺼져 있던 앱
- **WHEN** 리셋 30분 뒤 앱을 다시 켠다
- **THEN** 지연 규칙에 따라 자동으로 이어진다

### Requirement: 설정·확인 창·비용 안내
설정:
- 두 토글이 있어야 한다(SHALL): "사용량 한도 알림", "리셋되면 자동으로 이어서 하기". 둘 다 기본 켬이다(SHALL).
- 자동 재개 설명은 한 줄이고 "이어서 하는 동안 사용량을 써요"를 포함해야 한다(SHALL).
- 자동 재개를 끄면 남은 예약은 모두 "직접 잇기"로 바뀌어야 한다(SHALL).

새 작업 폼:
- 전역 값을 기본으로 한 "리셋되면 자동으로 이어서 하기" 체크를 보여 줘야 한다(SHALL).
- 배포 유형이나 원격 조작이면 체크를 끄고 이유를 한 줄로 보여 줘야 한다(SHALL).

위험 모드 확인 창:
- auto·bypassPermissions의 네이티브 확인 창에는 "리셋 후 자동으로 이어서 하기" 체크박스가 있어야 한다(SHALL). 기본은 해제다.
- 체크 상태는 그 작업에만 저장해야 한다(SHALL).

#### Scenario: 전역 끄기
- **WHEN** 대기 예약 2개가 있는 상태에서 자동 재개를 끈다
- **THEN** 리셋 후에도 실행되지 않는다
- **AND** 두 카드에 직접 잇기 버튼이 보인다

### Requirement: 단계적 출시
- 재개 동작 실측(스파이크)이 끝나 활성화 플래그가 켜지기 전에는, 자동 재개 예약을 실행하지 않아야 한다(MUST NOT). 이 동안 한도 감지·알림·배너·직접 잇기만 동작해야 한다(SHALL).
- 플래그가 꺼져 있으면 알림·배너에 자동 재개 문구를 넣지 않아야 한다(SHALL).

#### Scenario: 스파이크 전
- **WHEN** 활성화 플래그가 꺼진 빌드에서 작업이 한도에 닿는다
- **THEN** 알림과 배너는 "직접 이어야 해요"로만 보인다
- **AND** 리셋 후에도 CLI가 실행되지 않는다

### Requirement: 세션 id 인자 검증
- 앱이 CLI에 넘기는 bg id는 `-`로 시작하면 거부해야 한다(SHALL). 대상은 stop·logs·attach다.
- 재개용 세션 id는 소문자 UUID가 아니면 거부해야 한다(SHALL).

#### Scenario: 옵션처럼 보이는 id
- **WHEN** bg id `-h`로 멈추기나 로그를 요청한다
- **THEN** 잘못된 세션 ID 오류가 나고 CLI가 실행되지 않는다
