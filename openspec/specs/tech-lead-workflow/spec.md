# tech-lead-workflow Specification

## Purpose
D.Duck에서 시작하는 백그라운드 작업이 역할 분리, 명확한 브리프, 격리, 한계 설정, 새 눈 검증, 검토 용량이라는 테크 리드 방식으로 돌아가게 한다.

## Requirements

### Requirement: 번들 팀 역할
앱은 dduck-developer, dduck-qa, dduck-reviewer, dduck-security, dduck-release, dduck-researcher, dduck-writer 역할을 번들해야 한다(SHALL). 페르소나를 따로 고르지 않은 작업에 유형이 있으면 그 유형의 역할을 `--agents` JSON과 `--agent`로 그 세션에만 주입해야 하며(SHALL), 사용자·프로젝트 설정 파일을 만들거나 바꾸지 않아야 한다(MUST NOT). 역할은 백엔드가 작업 유형으로 정해야 하며 웹뷰가 역할 정의·팀 규칙·도구 목록을 보낼 수 없어야 한다(MUST NOT). reviewer·security·qa 역할에는 Edit/Write 도구가 없어야 하고(SHALL), reviewer·security는 `git diff/log/show/status`만 확인 없이 쓸 수 있어야 한다(SHALL).

#### Scenario: 검토 유형 작업
- **WHEN** 사용자가 페르소나 없이 "검토" 유형으로 작업을 시작한다
- **THEN** `--agents`에 dduck-reviewer 정의(도구 Read, Glob, Grep과 git 읽기 명령 4개, AG-15)가 들어가고 `--agent=dduck-reviewer`, `--allowedTools`에 git 읽기 명령, 권한 manual로 시작된다

#### Scenario: 사용자 페르소나 우선
- **WHEN** 사용자가 "검토" 유형에 페르소나 design-critic을 고른다
- **THEN** `--agent=design-critic`으로 시작되고 번들 역할은 주입되지 않는다

### Requirement: 작업 유형 프리셋
유형을 고르면 작업 창이 역할, 권한, effort, worktree 기본값을 채워야 하고(SHALL), 사용자가 바꾼 값이 우선해야 한다(SHALL). effort는 `--effort=<level>`로 넘겨야 한다(SHALL). 유형을 고른 작업은 확인을 건너뛰는 권한을 쓸 수 없어야 하며, 웹뷰가 요청해도 백엔드가 거부해야 한다(MUST NOT). 검토·보안·리서치 유형의 기본 권한은 매번 확인이다.

#### Scenario: 개발 유형 기본값
- **WHEN** 사용자가 "개발"을 고른다
- **THEN** 권한이 "계획만 세우기", effort가 high로 채워지고, 안전한 git 저장소면 worktree가 켜진다

#### Scenario: 배포 유형의 위험 모드
- **WHEN** 웹뷰가 "배포" 유형에 bypassPermissions로 시작을 요청한다
- **THEN** 작업을 시작하지 않고 오류를 표시한다

### Requirement: 구조화 브리프
작업 창은 목표(필수), 범위 밖, 제약, 완료 기준을 따로 입력받아야 하고(SHALL), 비어 있지 않은 칸만 정해진 제목(`## 목표`, `## 범위 밖 (손대지 말 것)`, `## 제약`, `## 완료 기준`) 아래에 넣어 지시를 만들어야 한다(SHALL). 조립된 지시는 시작 전에 미리 볼 수 있어야 한다(SHALL).

#### Scenario: 브리프 조립
- **WHEN** 사용자가 목표와 완료 기준만 적는다
- **THEN** 지시는 "## 목표"와 "## 완료 기준" 두 부분으로 만들어지고 미리보기에 보인다

### Requirement: 팀 규칙
D.Duck이 시작하는 모든 백그라운드 작업에는 번들된 팀 규칙을 `--append-system-prompt`로 붙여야 한다(SHALL). 규칙에는 범위 준수, 막힘 보고 후 멈춤, 자격증명 입력·인증 우회 금지, 기본 브랜치 직접 커밋·push 금지, 배포·결제·삭제·외부 전송 전 멈춤, 공유 인터페이스 변경 시 SendMessage 알림, 4부분 보고가 들어가야 한다(SHALL).

#### Scenario: 규칙 부착
- **WHEN** 어떤 유형이든 작업을 시작한다
- **THEN** 인자에 `--append-system-prompt=`로 시작하는 팀 규칙 한 인자가 `--` 앞에 들어간다

### Requirement: worktree 격리
작업 창은 작업 폴더가 안전한 git 저장소일 때 worktree 격리(`--worktree=<이름>`)를 고를 수 있게 해야 한다(SHALL). 개발 유형은 안전한 저장소에서 기본으로 켜고, 그 밖의 유형은 기본으로 끈다(실측: AG-16). 저장소가 아니거나, 루트가 홈 폴더이거나, 커밋이 없으면 고를 수 없고 이유를 보여야 한다(SHALL). 판정에 git 명령을 실행하지 않아야 한다(MUST NOT). worktree 이름은 백엔드가 작업 이름에서 `[A-Za-z0-9._-]`만 남겨 만들고 `..`를 허용하지 않아야 한다(SHALL).

#### Scenario: 홈 폴더 저장소
- **WHEN** 작업 폴더의 git 루트가 홈 폴더다
- **THEN** worktree 선택이 꺼지고 "홈 폴더 저장소라 격리할 수 없습니다"가 보인다

### Requirement: 민감 영역
브리프에서 "돈·인증·데이터 저장을 건드림"을 켜면 권한은 계획만 세우기·매번 확인만 고를 수 있어야 하고(SHALL), effort는 최소 xhigh여야 하며(SHALL), 위험할 수 있는 페르소나는 거부해야 한다(SHALL). 백엔드가 이 조건을 다시 확인해야 한다(SHALL). 이는 웹뷰가 보낸 표시에 의존하는 안전장치이며 보안 경계가 아니다.

#### Scenario: 민감 영역 권한 상한
- **WHEN** 민감 영역을 켠 채 웹뷰가 acceptEdits로 시작을 요청한다
- **THEN** 작업을 시작하지 않고 오류를 표시한다

### Requirement: 새 눈 후속 검증
개발 유형 작업이 검토 필요 또는 완료 상태면 카드와 상세에 "QA 맡기기", "리뷰 맡기기"가 보여야 한다(SHALL). 누르면 새 작업 창이 그 세션의 실제 작업 폴더(worktree였다면 그 경로), worktree 끔, QA 또는 검토 유형, 그 작업 이름(정리·64자)을 가리키는 목표로 채워져 열려야 하며(SHALL), 자동으로 시작하지 않고 이전 대화를 넘기지 않는 새 세션이어야 한다(SHALL). 상세에는 처음 지시로 작업 창을 채우는 "이 브리프로 다시 맡기기"가 있어야 한다(SHALL).

#### Scenario: 리뷰 맡기기
- **WHEN** 사용자가 완료된 개발 작업 "fix-flaky-test"에서 "리뷰 맡기기"를 누른다
- **THEN** 작업 창이 "검토" 유형, 같은 폴더, 목표 "'fix-flaky-test' 작업의 변경을 리뷰"로 채워져 열린다

### Requirement: 막힌 것부터
에이전트 페이지 머리말은 검토 필요 작업 수를 보여 주고, 누르면 작업 보드의 검토 필요 열로 이동해야 한다(SHALL).

#### Scenario: 막힌 작업 바로가기
- **WHEN** 검토 필요 작업이 2개일 때 사용자가 "막힌 작업 2개 — 먼저 풀기"를 누른다
- **THEN** 작업 페이지가 열리고 검토 필요 열로 스크롤된다

### Requirement: 검토 용량
설정에 "하루에 제대로 읽을 수 있는 변경 수"(1–10, 기본 3)가 있어야 한다(SHALL). D.Duck이 시작한 개발·배포 유형 작업 중 아직 "검토함" 표시를 하지 않은 작업(완료 포함)의 수가 용량 이상이면, 새 개발·배포 작업을 시작할 때 경고하고 "그래도 시작"을 한 번 더 눌러야 시작해야 한다(SHALL). 에이전트 페이지 머리말에 "검토 용량 N/M"을 보여야 하고(SHALL), 개발·배포 작업 카드에는 "검토함" 동작이 있어야 한다(SHALL).

#### Scenario: 용량 초과
- **WHEN** 용량이 3이고 진행 중인 개발 작업이 3개일 때 새 개발 작업을 시작한다
- **THEN** "검토 용량을 넘깁니다" 경고와 "그래도 시작" 버튼이 보이고, 누르기 전에는 시작하지 않는다

#### Scenario: 검토함 표시
- **WHEN** 완료된 개발 작업 3개가 있어 용량 3/3일 때 하나에 "검토함"을 누른다
- **THEN** 검토 용량이 2/3이 되고 새 개발 작업이 경고 없이 시작된다

#### Scenario: 막힘 보고
- **WHEN** 작업이 "막힘:"으로 보고하고 멈춰 CLI가 그 세션을 blocked로 표시한다
- **THEN** 작업 보드의 검토 필요 열에 나타나고 막힌 작업 수에 포함된다

### Requirement: 휴대폰 알림
설정에 "휴대폰으로 알림(Remote Control)"을 두어야 하며 기본값은 꺼짐이어야 한다(SHALL). 켤 때는 앱 백엔드가 "Claude 계정이 로그인된 휴대폰이 이 Mac의 작업에 지시를 보내고 승인할 수 있게 됩니다"를 알리는 네이티브 확인 창으로 승인을 받아야 한다(SHALL). 켜져 있으면 새 작업 창의 "휴대폰으로 알림"이 기본 체크되고, 백엔드는 `--remote-control=<이름>`(백엔드가 `[a-z0-9-]`로 만든 이름)으로 시작해야 한다(SHALL). 위험 권한 모드, 민감 영역, 배포·보안 유형 작업에서는 백엔드가 이 옵션을 거부해야 한다(MUST NOT).

#### Scenario: 위험한 작업의 원격 조작 (1)
- **WHEN** 휴대폰 알림이 켜진 상태에서 민감 영역 작업을 시작한다
- **THEN** 그 작업은 원격 조작 없이 시작된다

### Requirement: 작업 알림
팀 규칙에는 "끝났거나 결정·답이 필요해 멈추기 직전에 PushNotification으로 한 줄(코드·경로·비밀값 없이) 알린다"가 있어야 한다(SHALL). 도구 권한 승인은 Claude Code가 띄우므로 모델이 미리 알릴 수 없고, 사용자가 Mac 앞에 있으면 Claude Code가 알림을 생략할 수 있다. D.Duck의 macOS 알림은 답 기다림뿐 아니라 완료·실패 전이에도 작업 이름과 상태만으로 보내야 하며(SHALL), 설정으로 끌 수 있어야 한다(SHALL).

#### Scenario: 자리를 비운 사이 작업 완료
- **WHEN** 휴대폰 알림을 켠 작업이 사용자가 자리를 비운 동안 끝난다
- **THEN** 작업이 Claude 앱으로 "한 일" 한 줄 알림을 보내고, D.Duck은 macOS 알림으로 완료를 알린다

#### Scenario: 위험한 작업의 원격 조작
- **WHEN** 웹뷰가 배포 유형 작업에 휴대폰 알림을 켜서 시작을 요청한다
- **THEN** 백엔드가 거부하고 오류를 표시한다

#### Scenario: 처음 켜기
- **WHEN** 사용자가 설정에서 휴대폰 알림을 켠다
- **THEN** 네이티브 확인 창이 원격 조작 범위를 설명하고, 취소하면 꺼진 상태로 남는다

### Requirement: 작업 지시 기록
D.Duck 작업 창으로 시작한 작업은 사용자가 적은 지시(조립된 브리프), 작업 이름, 폴더, 유형, 페르소나, 시작 시각을 앱 DB에 남겨야 한다(SHALL). 이는 사용자가 D.Duck에 직접 적은 내용이라 transcript 원문 비저장 원칙의 예외다(D-050과 같은 근거). 작업 카드와 상세는 이 기록을 먼저 보여 주고, 없을 때만 transcript에서 읽는다(SHALL). 작업 페이지에는 `claude agents` 목록에서 사라진 작업까지 최신순으로 보여 주는 "지난 작업" 목록이 있어야 하며(SHALL), 항목마다 지시 보기, "이 브리프로 다시 맡기기", 지우기를 제공해야 한다(SHALL). 지우면 지시가 DB와 WAL에서 사라져야 한다(SHALL). 설정에 "작업 지시 저장"(기본 켬)과 "지난 작업 모두 지우기"를 둔다(SHALL). 터미널에서 직접 시작한 세션의 지시는 저장하지 않는다.

#### Scenario: 끝난 작업의 지시 보기
- **WHEN** 이틀 전에 D.Duck으로 시작한 작업이 `claude agents` 목록에서 사라졌다
- **THEN** 작업 페이지의 "지난 작업"에서 그 작업의 지시, 유형, 폴더, 시작 시각을 볼 수 있다

#### Scenario: 지시 지우기
- **WHEN** 사용자가 지난 작업 하나를 지운다
- **THEN** 목록에서 사라지고 그 지시문이 DB·WAL 파일 바이트에 남지 않는다

#### Scenario: 저장 끄기
- **WHEN** 설정에서 "작업 지시 저장"을 끄고 새 작업을 시작한다
- **THEN** 그 작업의 지시는 저장되지 않고 카드에는 transcript에서 읽은 처음 지시가 보인다
