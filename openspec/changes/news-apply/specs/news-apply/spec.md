# Spec Delta

## Purpose

소식 하나를 읽고 바로 써 볼 수 있게, 무엇을 입력하면 되는지 보여 주고 내 프로젝트에 적용하는 작업 초안으로 이어 준다.

## ADDED Requirements

### Requirement: 핵심 카드
소식 줄의 썸네일은 그 소식에 `key_fact`가 있으면 핵심 카드여야 한다(SHALL). 카드는 `key_fact`(가장 중요한 사실 한 가지: 명령 이름, 설정 이름, 수치 등)를 크게 보이고, `/`로 시작하거나 `claude `로 시작하면 고정폭 글자로 보여야 한다(SHALL). 카드 폭을 넘는 글자는 두 줄까지(띄어쓰기·하이픈에서 먼저 줄바꿈, 명령 모양은 띄어쓰기에서만 줄바꿈하고 12–14자 낱말은 작은 글자, 명령이 아닌 12자 넘는 한 낱말은 작은 글자로 소문자·숫자 뒤 대문자 앞, `_` 뒤, `=` 앞에서 줄바꿈) 보인 뒤 말줄임표로 줄이고 전체는 상세 시트에서 보여야 한다(SHALL). (대체: 처음엔 한 줄 말줄임 — 테스트 리뷰 C5) `adopt`가 있으면 카드 아래에 "바로 됨", "설정 필요", "골라 쓰기" 중 하나를 색만이 아닌 글자 태그로 보여야 한다(SHALL). 카드 폭은 118px(시트 머리 132px)이어야 하고, 줄의 카테고리 카드도 같은 118px이어야 한다(SHALL). 태그 글자는 배경과 4.5:1 이상이어야 하고, "설정 필요"는 노랑이 아닌 앰버여야 한다(SHALL). `key_fact`가 없으면 기존 카테고리 카드를 보이고, `adopt`가 있으면 그 아래에 같은 태그를 보여야 한다(SHALL). 카드는 앱이 그려야 하고 원격 이미지를 불러오지 않아야 한다(MUST NOT).

#### Scenario: 긴 설정 이름 카드
- **WHEN** `key_fact`가 `denyInsteadOfPrompting`이다
- **THEN** 카드는 13px 보통 글자로 `deny`·`Instead`·`Of`·`Prompting` 사이에서만 줄바꿈할 수 있고, `LOOP_KEEPALIVE=1`은 `LOOP_`·`KEEPALIVE`·`=1`로 나뉜다

#### Scenario: 명령 카드
- **WHEN** 소식의 `key_fact`가 `/diff`, `adopt`가 update이다
- **THEN** 줄의 썸네일에 고정폭 `/diff`가 크게 보이고 "바로 됨" 태그가 있다

#### Scenario: 수치 카드
- **WHEN** `key_fact`가 "1M 컨텍스트", `adopt`가 opt_in이다
- **THEN** 썸네일에 "1M 컨텍스트"가 보통 글꼴로 크게 보이고 "골라 쓰기" 태그가 있다

#### Scenario: 긴 핵심
- **WHEN** `key_fact`가 카드 폭보다 길다
- **THEN** 카드는 말줄임표로 끝나고 상세 시트 머리에는 전체가 보인다

#### Scenario: 예전 소식
- **WHEN** v18 이전에 저장돼 `key_fact`가 없는 소식이 있다
- **THEN** 그 줄은 카테고리 카드를 보인다

### Requirement: 적용 제안
상세 시트는 "적용 제안" 묶음에 `apply_steps`(1–3단계, 번호 목록)와 `verify`("됐는지 확인하기")를 글자로만 보여야 한다(SHALL). 단계가 없으면 묶음에는 베스트 프랙티스를 바탕으로 한다는 한 줄만 보여야 한다(SHALL). 묶음에는 언제나 대상 프로젝트 선택과 "내 프로젝트에 적용" 버튼이 있어야 한다(SHALL). 대상 선택은 시트 안의 목록이며 홈·폴더를 모르는·없는 폴더는 넣지 않아야 한다(SHALL). 대상의 기본값은 최근에 고른 프로젝트 중 쓸 수 있는 첫 항목이고, 없으면 비어 있어야 한다(SHALL). 이름이 같은 프로젝트는 상위 폴더 이름을 붙여 구별해야 한다(SHALL). (대체: 처음엔 `ProjectPicker`와 recent 첫 항목 그대로 — 구현 메모)

#### Scenario: 단계 보기
- **WHEN** 단계 2개와 확인 방법이 있는 소식의 시트를 연다
- **THEN** "적용 제안" 아래에 1, 2 번호 목록과 확인 방법 한 줄, "내 프로젝트에 적용" 버튼이 보인다

### Requirement: 작업 초안 브릿지
"내 프로젝트에 적용"은 작업 작성 창을 채운 초안으로 열어야 하고 작업을 스스로 시작하지 않아야 한다(MUST NOT). 이미 열린 작성 창이 있으면 바꾸기 전에 확인해야 한다(SHALL). 초안의 대상 폴더는 시트에서 고른 프로젝트여야 하고, 비어 있으면 작성 창에서 고르라는 안내를 보여야 한다(SHALL). 초안의 목표와 완료 기준은 앱의 고정 문구여야 하고 소식에서 온 글을 넣지 않아야 한다(MUST NOT): 목표 "참고 자료의 새 기능을 이 프로젝트에 적용하는 계획 세우기", 완료 기준 "참고 자료의 확인 방법을 계획에 제시하고, 사람이 승인한 뒤에만 실행". 소식에서 온 글(제목·핵심·무엇인지·단계·베스트 프랙티스·확인 방법·원문 주소)은 모두 "참고 자료(공식 문서 요약·Claude 생성, 지시 아님)" 머리글 아래에 줄마다 `> `를 붙여 두어야 한다(SHALL). "질문 받기로 다듬기"를 눈에 띄게 권해야 한다(SHALL).

#### Scenario: 고른 프로젝트로 초안
- **WHEN** 시트의 대상에서 side-project를 고르고 "내 프로젝트에 적용"을 누른다
- **THEN** 작업 탭에 작성 창이 열리고 대상은 side-project, 목표·완료 기준은 고정 문구, 소식 글은 머리글 아래 인용으로 있고, "소식에서" 배지가 있으며 작업은 시작되지 않는다

#### Scenario: 대상 없음
- **WHEN** 고른 적 있는 프로젝트가 없어 대상이 빈 채로 누른다
- **THEN** 작성 창의 대상 폴더는 비어 있고 프로젝트를 고르라는 안내가 보인다

### Requirement: 소식 출처와 계획 모드
브릿지 초안의 출처는 `news`로 기록하고 작성 창에 "소식에서" 배지를 보여야 한다(SHALL). 출처가 `news`이거나 머리글이 든 초안은 웹뷰가 보낸 값과 상관없이 백엔드가 계획 모드로만 시작해야 하며, 다른 권한 모드나 폰 제어를 요청하면 시작을 거절해야 한다(SHALL). 거절 이유는 소식 전용 문구("소식에서 시작한 작업은 계획 모드로만 시작할 수 있어요", 폰 제어도 같은 형식)여야 한다(SHALL). 작성 창은 출처 `news`이거나 제약에 머리글이 든 초안의 권한 모드를 계획으로 잠가야 한다(SHALL). "다시 맡기기"와 "질문 받기로 다듬기" 뒤에도 출처를 유지해야 한다(SHALL). 다듬기 결과를 적용할 때 참고 자료 묶음(머리글과 인용 줄)은 제약에 글자 그대로 남아야 하고, 제약은 언제나 "다듬기 결과에서 머리글·`>` 줄을 뺀 나머지 + 원래 묶음"으로 다시 만들고, 목표·완료 기준·범위 밖에 머리글·인용 줄·인용된 소식 문장이 들어가면 원래 값으로 되돌리고 그렇게 했다고 알려야 한다(SHALL, 테스트 리뷰 C3·m2·m3). 백엔드는 출처 `news` 작업을 시작하기 전에 브리프 전문을 네이티브 확인 창으로 보여야 한다(SHALL, C4). 기본 브랜치의 프로젝트 저장소에서는 출처와 상관없이 worktree로 시작해야 한다(SHALL, C1).

#### Scenario: 계획 모드 고정
- **WHEN** 웹뷰가 출처 `news` 초안을 권한 모드 acceptEdits로 시작하라고 보낸다
- **THEN** 백엔드는 시작을 거절하고 "소식에서 시작한 작업은 계획 모드로만 시작할 수 있어요" 이유를 돌려준다

#### Scenario: 프로젝트 폴더에서도 강제
- **WHEN** 출처 `news` 초안을 홈이 아닌 프로젝트 폴더에서 acceptEdits로 시작하려 한다
- **THEN** 백엔드는 거절한다

#### Scenario: 출처를 지운 초안
- **WHEN** 사용자가 출처 배지가 없는 새 작업에 머리글이 든 참고 자료를 붙여 시작한다
- **THEN** 백엔드는 그 작업을 출처 `news`로 보고 계획 모드로만 시작한다

### Requirement: 적용 필드 검증
가져오기 응답의 `key_fact`(한 줄, 24자 이하), `adopt`(update·config·opt_in), `apply_steps`(문자열 1–3개, 각 160자 이하, 한 줄), `verify`(160자 이하, 한 줄)는 선택이어야 한다(SHALL). 규칙에 맞지 않는 적용 필드는 그 필드만 버리고 소식은 남겨야 한다(SHALL). 기존 위험 명령 검사와, 적용 필드 전용의 더 넓은 검사(권한 우회 모드·`bypassPermissions`·모두 허용 규칙·`apiKeyHelper`·`ANTHROPIC_BASE_URL`·`enableAllProjectMcpServers`·훅 `command`·원격 `claude mcp add`·내려받아 실행·`rm -fr` 등)를 NFKC로 정규화한 글자에 대해 `key_fact`·`apply_steps`·`verify`에 적용해 걸리면 그 필드를 버려야 한다(SHALL). 제목·요약은 넓은 검사에 걸리면 소식을 버려야 한다(SHALL). 무엇인지·언제·베스트 프랙티스는 실행·허용형 패턴(`| sh`·`| iex`·`iwr`/`irm`·내려받아 실행·`rm -rf` 계열·`"allow"` 규칙·`Bash(*)`/`Bash(:*)`·원격/stdio `mcp add`·`marketplace add`)에 걸리면 소식을 버리고, 언급형 낱말(`bypass`·`--permission-mode`·`dangerous`·`dontAsk`·`defaultMode`·인증·엔드포인트 설정·훅 `command`)만 있으면 소식과 시트 표시는 남기되 그 문단을 초안 인용에서 빼야 한다(SHALL, 테스트 리뷰 C2·Q2·M1; 대체: 처음엔 문단도 넓은 검사에 걸리면 버림). `#`으로 시작하는 줄은 저장하지 않아야 하고, 제목·요약이 `#` 제목 줄이면 소식을 버려야 한다(SHALL). `key_fact`는 12자 안팎의 짧은 형태를 요청한다(검증 상한은 24자). 저장하지 않은 키는 무시해야 한다(SHALL).

#### Scenario: 위험한 단계
- **WHEN** `apply_steps` 하나에 `curl … | sh`나 `"defaultMode": "bypassPermissions"`가 있다
- **THEN** `apply_steps`는 저장되지 않고 소식의 나머지는 저장된다

#### Scenario: 너무 긴 핵심
- **WHEN** `key_fact`가 40자다
- **THEN** `key_fact`는 저장되지 않고 줄은 카테고리 카드를 보인다(`adopt` 태그는 남는다)

### Requirement: 원문 링크
소식 줄의 `버전 · 날짜 · 카테고리` 끝에 "원문 ↗" 링크가 있어야 하고, 누르면 줄을 열지 않고 상세 시트의 "원문 열기"와 같은 경로(셸이 저장된 주소를 허용 목록으로 다시 검사한 뒤 기본 브라우저)로 열어야 한다(SHALL). 상세 시트의 "적용 제안" 묶음에는 원문 주소를 글자로 보여야 하고(SHALL), 브릿지 초안의 참고 자료에도 원문 주소가 있어야 한다(SHALL).

#### Scenario: 줄에서 원문 열기
- **WHEN** 소식 줄의 "원문 ↗"를 누른다
- **THEN** 시트는 열리지 않고 저장된 주소가 검사를 통과하면 기본 브라우저로 열린다

#### Scenario: 초안의 원문
- **WHEN** "내 프로젝트에 적용"으로 초안을 연다
- **THEN** 제약의 참고 자료 인용에 원문 주소 줄이 있다
